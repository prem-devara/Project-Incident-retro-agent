Google Cloud service disruption, June 12, 2025 (all times US/Pacific)

Summary
Google Cloud, Google Workspace and Google Security Operations products experienced increased 503 errors in external API requests, impacting customers. Regions/Zones: Global.

System setup
Google and Google Cloud APIs are served through Google API management and control planes. Distributed regionally, these management and control planes are responsible for ensuring each API request that comes in is authorized, has the policy and appropriate checks (like quota) to meet their endpoints. The core binary that is part of this policy check system is known as Service Control. Service Control is a regional service that has a regional datastore that it reads quota and policy information from. This datastore metadata gets replicated almost instantly globally to manage quota policies for Google Cloud and customers.

May 29, 2025
A new feature was added to Service Control for additional quota policy checks. This code change and binary release went through a region by region rollout, but the new code path was never exercised during this rollout because it needed a policy change to trigger it. The code change came with a red-button to turn off that particular policy serving path.

June 12, 2025
~10:45 A policy change was inserted into the regional Spanner tables that Service Control uses for policies. This metadata was replicated globally within seconds. This policy data contained unintended blank fields. Service Control then regionally exercised quota checks on policies in each regional datastore. This pulled in blank fields for this policy change and exercised the new code path, which hit a null pointer and caused the binaries to go into a crash loop. This occurred globally, in each regional deployment.

~10:47 Within 2 minutes, the Site Reliability Engineering team was triaging the incident.
~10:55 Within 10 minutes, the cause was identified and the red-button (to disable the serving path) was being put in place.
~11:10 The red-button was ready to roll out, ~25 minutes from the start of the incident.
~11:25 Within 40 minutes of the incident, the red-button rollout was completed, and recovery started across regions, starting with the smaller ones first.

In some larger regions, such as us-central1, as Service Control tasks restarted, it created a herd effect on the underlying infrastructure it depends on (the Spanner table), overloading that infrastructure. The team throttled task creation to minimize the impact on the underlying infrastructure and routed traffic to multi-regional databases to reduce the load. It took up to ~2h 40 mins to fully resolve in us-central1.

Communication: The first incident report was posted to Cloud Service Health ~1h after the start of the crashes, because the Cloud Service Health infrastructure was down due to this outage. For some customers, the monitoring infrastructure they had running on Google Cloud was also failing, leaving them without a signal of the incident or an understanding of the impact.

Customer impact
Customers had intermittent API and user-interface access issues to the impacted services. Existing streaming and IaaS resources were not impacted. Affected products included Identity and Access Management, Cloud Storage, BigQuery, Compute Engine, Cloud Run, Cloud Spanner, Cloud SQL, Pub/Sub, Cloud Monitoring, Cloud Logging, Vertex AI, the Google Cloud Console and many other Google Cloud products, plus Google Workspace products including Gmail, Google Drive, Google Docs, Google Meet, Google Calendar and Google Chat. Several products had residual impact (e.g. backlogs) for some time after the primary issue was mitigated.
